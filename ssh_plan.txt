WHAT THE MEASUREMENTS SHOW
--------------------------
Training SSH-Bruteforce (94,041 rows): median 374,609 us duration, 22 fwd / 22 bwd pkts,
  Flow IAT Mean 8,686 us.
- Attempt 3 (Java) packet counts were far too low (2 / 3). Attempt 4-5 (Hydra) packet
  counts now match training (18-24). Bundling several attempts per connection did
  change the shape.
- Attempts 4-5 have the right packet count but flows ~46-52x too long, because each
  packet gap is ~47-53x training's. The per-packet timing is the remaining mismatch.
- Time units: the Python converter writes seconds, training uses microseconds. The
  seconds-to-microseconds scaling was checked (unit check = 1.0000, fwd_iat_tot =
  flow_duration) and the round-trip test (5,000 training rows written in Python format,
  read back through the live pipeline) gave zero error and 100% agreement.
- Column meaning: even after the round-trip test, the Python converter's values differ
  from training on the same SSH traffic (examples: ACK Flag Count training median 0 vs
  Python 40; Fwd Pkt Len Min training 0 vs Python 66; Flow IAT Min training 4 us vs
  Python 0). The Java converter matches training better on these features (ACK median
  4; Flow IAT Min median 34 us) but is not identical.
  So the Python converter is not a like-for-like substitute for the Java converter,
  and its 0% results cannot be read as the model's performance on Hydra traffic.

STEP 1 - CONVERT WITH THE JAVA CONVERTER (next step, no new attack needed)
--------------------------------------------------------------------------
Goal: produce features with the same converter the training data used.
  - On the attacker Kali, check the pcap is still there:
        ls -la kali_to_kali_attack.pcap
    If it is, no new attack is needed.
  - Run the Java CICFlowMeter-v3 on it with the same command as attempt 3.
  - Rename the output to kali_to_kali_java.csv.
  - Send it to F:\all_10_csv_manual\ (Windows will run the same analysis).
  - If the pcap is gone, a new Hydra run is needed, captured to pcap and converted
    with the Java tool.

STEP 2 - 1-SECOND FLOW WINDOWS (for per-second results)
-------------------------------------------------------
Training SSH flows are under 0.6 s (max 567,266 us), so a 1-second flow timeout cuts no
training-length flow.
  - Find the flow timeout in the converter on Kali (do not assume the name):
      Java: grep -rni "timeout" <CICFlowMeter source>
  - Set it to 1 second (1,000,000 us in the Java tool, or 1 in Python-tool seconds).
    Confirm units in the source first. Rebuild if the Java source was changed.
  - Re-convert the same pcap. Check max(flow_duration) <= 1 s and the row count before
    sending.
  - Per-second rows let live_detect.py show a per-second table.
  - Limit: 1-second windows still carry the per-packet gap (~0.4 s), so each window
    holds only ~2-3 packets. Shorter windows alone will not make the model recognize
    the attack. The gap must be understood first (see STEP 3).

STEP 3 - FIND WHERE THE PER-PACKET GAP COMES FROM (not yet done)
-----------------------------------------------------------------
  - Check the pcap's packet timestamps on the attacker Kali (tshark, or Wireshark
    IO graph) for the attack connection. Check whether the ~0.4 s gaps come from the
    victim's sshd (slow auth response), from Hydra waiting between tries, or from the
    network.
  - Only after that is known, decide whether the attack setup should change.

STEP 4 - LIVE DETECTION (after STEPS 1-3)
-----------------------------------------
  - 2_xgboost_model/live_detect.py: follow mode re-reads a growing CSV every second,
    scores only new rows, and prints a per-second table. Replay mode scores a whole
    file once (tested on kali_to_kali_attack.csv: works, 0% attack flagged, as expected
    for that file).
  - Follow mode is not tested yet. It needs a growing CSV from a live converter run.
  - Output is console only. No report or CSV files are written.

RULES
-----
- Do not edit attack or flow values to make the model detect them. Fix the converter
  or the traffic, then re-test.
- Do not re-tune Patator threads or sshd MaxAuthTries blindly. Attempts 1-2 failed
  in opposite directions.
- Check every column, unit and flow shape against the actual file. State the measured
  fact, not a guess.
- Report exact errors, not guesses, when something breaks.
