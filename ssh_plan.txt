SSH BRUTE-FORCE LIVE TEST - RUNBOOK (v6: Kali-to-Kali, Patator, 1-second flows)
=============================================================================

GOAL
----
Capture a real SSH brute-force attack, convert it with the SAME converter and the SAME
units as the training data, cut it into 1-second flow rows, move the CSV to Windows,
and score it with the trained 2-level model. Report whatever the model says.
No values are edited, scaled by hand, or re-labelled to improve a result.

INPUT FEATURES (decided)
-----------------------
- The saved models were trained on 78 features (2_xgboost_model/data/meta.json).
- 8 of them are never used in any tree split in either model (checked in the saved JSON):
    Bwd PSH Flags, Bwd URG Flags, Fwd Byts/b Avg, Fwd Pkts/b Avg, Fwd Blk Rate Avg,
    Bwd Byts/b Avg, Bwd Pkts/b Avg, Bwd Blk Rate Avg
- The other 70 features are used. The models need all 78 columns in order, so the
  8 unused columns are kept in the input and filled with 0. A 70-column input would
  fail, and a 70-feature model would need retraining (a different model, own test).
- Pending check (not yet run): on the training test rows, predict with the 8 columns
  as in the data, with them set to 0, and with them set to random non-zero values.
  Pass = identical predictions on every row in all three runs. Until it passes, the
  claim is "the saved trees never split on these 8", not "they cannot change any output".

WHY EACH STEP IS HERE (measured, see CLAUDE.md)
------------------------------------------------
- Training SSH flows: median 0.37 s, 22 fwd / 22 bwd packets, Flow IAT Mean 8,686 us.
- Python cicflowmeter (snake_case names) gave 17-19 s flows with the right packet count,
  but its flag and window values differ from training. So it is NOT used any more.
- Java CICFlowMeter-v3 is the converter CICIDS2018 used. It writes time in MICROSECONDS,
  which matches training. So no unit conversion is needed. Keep it that way.
- Flow timeout is set to 1 s so each flow row covers at most 1 s of traffic.

NETWORK / MACHINES
------------------
ATTACKER  = Kali VM (runs Patator, tcpdump, CICFlowMeter-v3). IP: <ATTACKER_IP>
VICTIM    = second Kali VM with openssh-server.                  IP: <VICTIM_IP>
WINDOWS   = F:\all_10_csv_manual (trained model lives here).
Check the IPs on each VM first:  ip a
Both VMs must be on the same network (same as attempts 4-5).

============================================================================
PART A - VICTIM KALI (run once)
============================================================================
A1. Install and start the SSH server:
      sudo apt update
      sudo apt install -y openssh-server
      sudo systemctl enable --now ssh
      sudo systemctl status ssh          (must show "active (running)")

A2. Create the test account (skip if it already exists):
      sudo adduser <USER>                (set a password you will put in the wordlist)

A3. Confirm the victim's IP:
      ip a                               (note <VICTIM_IP>)

Do NOT change any sshd setting (no MaxAuthTries, no LoginGraceTime). Record the
sshd config as it is:  grep -v '^#' /etc/ssh/sshd_config | grep .  > ~/sshd_used.txt

============================================================================
PART B - ATTACKER KALI: CONVERTER SETTING (one-time change)
============================================================================
B1. Find the flow timeout settings in the Java converter source. Do not guess names:
      grep -rn "flowTimeout\|activityTimeout" <CICFlowMeter_source_dir>
    Write down each line you find, with its current value and unit.

B2. Set both timeouts to 1 second, in microseconds (the Java tool uses us):
      flowTimeout     = 1000000
      activityTimeout = 1000000
    Only change values that are in microseconds. Check the unit next to each value first.

B3. Rebuild the converter with the SAME build command you used for attempt 3.

B4. Verify the change took effect with the test in step D6 (max Flow Duration must be
    <= 1000000). Do not proceed if that check fails.

============================================================================
PART C - ATTACKER KALI: CAPTURE AND ATTACK
============================================================================
C1. Confirm the capture interface name:
      ip a                               (usually eth0; use the one with <ATTACKER_IP>)

C2. Start the capture BEFORE the attack. Filter to the victim and port 22:
      sudo tcpdump -i <IFACE> host <VICTIM_IP> and port 22 -w kali_patator.pcap

C3. In a second terminal, check Patator's options first (do not guess flags):
      patator ssh_login --help

C4. Run the attack (wordlist = the same file used in attempts 4-5):
      patator ssh_login host=<VICTIM_IP> user=<USER> password=FILE0 0=/path/to/wordlist.txt -x ignore:mesg='Authentication failed.'
    Let it finish. Note the start and end times.

C5. Stop tcpdump with Ctrl+C in its terminal.

C6. Check how long the capture really lasted:
      capinfos kali_patator.pcap
    (if capinfos is missing: tshark -r kali_patator.pcap -T fields -e frame.time_epoch | sort -n | sed -n '1p;$p')
    Record the duration. Do not assume 20-30 minutes.

============================================================================
PART D - ATTACKER KALI: CONVERT PCAP TO FLOW CSV
============================================================================
D1. Convert the pcap with the Java CICFlowMeter-v3, using the SAME command as attempt 3,
    with the input file kali_patator.pcap. Name the output:
      kali_patator_1s.csv
    If the output name differs, rename it:  mv <output>.csv kali_patator_1s.csv

D2. Check the header is the Java format (starts with "Flow ID,Src IP,Src Port,Dst IP,Dst Port,...").
      head -1 kali_patator_1s.csv

D3. Count the rows:
      wc -l kali_patator_1s.csv

D4. Keep only the attack flows (attacker -> victim, port 22). Print the count:
      awk -F, 'NR>1 && $2=="<ATTACKER_IP>" && $5=="22"' kali_patator_1s.csv | wc -l

D5. Confirm the time unit is microseconds (values are whole numbers of us, and
    Flow Duration is at most 1,000,000 if the 1 s timeout worked):
      awk -F, 'NR>1 {if($8>m)m=$8} END{print "max Flow Duration (us) =", m}' kali_patator_1s.csv

D6. VERIFICATION GATE (stop here if it fails):
      max Flow Duration must be <= 1000000.
      If it is larger, the timeout change in Part B did not take effect. Go back to B1.

D7. Measure packets per flow (training median: 22 fwd / 22 bwd):
      awk -F, 'NR>1 && $2=="<ATTACKER_IP>" && $5=="22"{print $9, $10}' kali_patator_1s.csv | sort -n | awk '{f[NR]=$1; b[NR]=$2} END{print "median fwd =", f[int(NR/2)+1], " median bwd =", b[int(NR/2)+1]}'
    (Column 9 = Total Fwd Packet, column 10 = Total Bwd packets in the Java header.)

D8. Measure the gap between packets from the pcap (training Flow IAT mean median: 8,686 us):
      tshark -r kali_patator.pcap -Y "tcp.port==22" -T fields -e frame.time_delta_displayed | sort -n | awk '{a[NR]=$1} END{print "median gap (s) =", a[int(NR/2)+1]}'
    Record the number. Do not change any setting to adjust it. Report it as measured.

D9. Count TCP connections (shows whether Patator reused connections):
      tshark -r kali_patator.pcap -q -z conv,tcp | tail -5
    Record the number of TCP conversations.

E2. Tell Claude "the file is there". Do not run any script on Windows yourself.

F2. Check the header is the Java format. If it is, run the analysis on the

F3. Score every flow with level 1, then level 2, and print:

      - level 2: final labels and mean percentage per attack class

      - per-second table (timestamp of each flow row)
      - the flow-shape numbers next to the training medians
    Whatever the model outputs is reported as is.
